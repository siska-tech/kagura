# 桜吹雪: 固定HUDと「確保ゼロ」の再検証（2026-10-31）

本記録の主な数値はSDK還元前の通常fw-ABCで測定したもの。
桜吹雪の演出・固定HUD・音声・OAM計算はデモPR、汎用EXT一括書込み・一時オブジェクト削減・
scalar register短縮経路は別のSDK PRとし、[SDK性能記録](micropython-sdk-performance.md)で独立評価する。
測定ログ: [連続運転](measurements/sakura-selected-2026-10-31.txt)、
[新規起動と非加速](measurements/sakura-cold-2026-10-31.txt)、
[過去の診断VM](measurements/sakura-diagnostic-2026-10-31.txt)。

SDK還元PR作成時の統合再確認では、最終`device`をRAM `.mpy`へ差し替え、
他の通信モジュールは通常fw-ABCの凍結版のまま使用した。統計なし20秒で
1155 COMMIT確認、57.72 displayed/s、全エラー0（[ログ](measurements/sakura-sdk-integration-2026-10-31.txt)）。
これは従来条件の57.58／59.94とは別構成で、性能を直接比較しない。
統計付き構成では追加RAM負荷による起動時MemoryErrorを確認したため、
新SDKを凍結したファームでの統計付き再測定は未実施。今回Flashは変更していない。
同じRAM差分構成の非加速はPCMなしで独立確認し、加速解除後と新規accelerate=Falseは
各3秒・18更新でPASS、全エラー0。両場面を1セッションで続けると後者の起動が
MemoryErrorとなったため、後者はsoft resetして再確認した。
これはRAM差分構成のメモリ制約で、通常fw-ABCでは両経路の連続確認も成功している。
[非加速ログ](measurements/sakura-sdk-nonaccelerated-2026-10-31.txt)と
[RAM制約の失敗ログ](measurements/sakura-sdk-ram-limit-2026-10-31.txt)も保存する。

## 結果と測定値の訂正

HUDを固定フィールドに置き換え、数字の字形・位置・色・前回値・転送ビューを再利用する。
RP2のMB整形も整数化した。既定の通常ファームで、20秒後に続く60秒では
heap標本の純増0 byte、GC検出0回、COMMIT適用確認後58.17回/秒だった。
統計なし20秒では1199回のCOMMIT適用を確認し、59.94 displayed/s、全エラー0。

別のsoft resetから既定設定を新規起動した最終確認では、統計なし20秒で1152回確認、
57.58 displayed/s（`selected-default-plain.txt`）。59.94は連続運転後の値であり、
初回から保証する値ではない。通常VMのフレーム確保はheap配置に影響される。

**`gc.mem_alloc()`の差分は総確保量ではない。** 復帰時に解放されるVM呼出しフレーム、
束縛メソッドの引数配列などは標本間に消える。これまでの資料の
「確保byte/更新」は、この点では**net heap growth（heap純増）**と読み替える必要がある。
`Stats`の表示・説明も訂正した。通常ファームで総確保ゼロとは主張しない。

診断専用ファームではVMフレームのCスタック側しきい値を44→256 byteに変え、
同じドライバ・アプリで統計あり／なし各20秒の**総確保0回・0 byte、GC 0回**を実測した。
これは製品に採用していない。実機と通常ビルドの構成はfw-ABCへ戻した。
この計測時点では共有ドライバを変更していない。その後SDK変更を別ブランチへ抽出した。
ボード設定・MicroPython本体・FPGA RTL・ABIは今回のPRでも変更しない。
診断VMの数値は過去の調査結果であり、今回のPR作業ではFlashを書き換えていない。

## 採用したコード

- `sakura_hud.py`: 3／9フィールドの位置・字形・色を固定配列に保持。
  40通りの転送長のmemoryviewを起動時に作り、dirty spanをバッファ先頭からpackする。
  行ごとに4 KBのstripを保持する必要もなくした。
- `sakura_hud_viper.py`: 数値整形、字形／フィールド差分、クリア・描画・packをViperで処理。
  大きなカーネルは背景・ピアノの読込み後に読み込む。
- `hudround`: float32入力、100倍の丸め、float32にparseした10進候補の比較まで整数で再現。
  実行時の浮動小数点形式と丸めを確認し、異なる形式・範囲外の値は従来の整形へ戻す。
- `hudglyph`: 位置・色・桁数が同じ場合は、変更した字形だけをdirtyにする。
  1桁だけの変更は最大2タイルで転送できる。
- `oam`: フレーム・層ごとに共通の除算を256枚のループ外へ移す。
  元の`build_oam`を残し、最適化カーネルは読込み後に選択する。
- `short`: 固定のレジスタ操作を既存の`Link._fast`に渡し、上位呼出し層を減らす。
  所有・abort・timeout・例外変換は同じラッパーを通す。
  `accelerate=False`／加速解除後／古いLinkでは従来のtransport経路を使う。
- 音声データのbase memoryviewを1つ保持し、初回の長さごとのビューを保持する際に
  毎回base viewを作らない。帯域計算は32 bitの2語で元の整数式と一致させる。
  PCM再生済サンプル数は、停止中・終了済みの音で大整数を作らず同じ値を返す。
- 単色クリア用の常駐データ4.5 KBをViperの塗りつぶしに置き換えた。
  読込み用workspaceも8→4 KBへ縮小。4／8 KBの両チャンクで全22ピアノ音が同じC版SHA-256に一致。
- `ipoll`の再利用tupleを入力読取りなしで起動時に確保する。
  保留中のキーを消費しないこともテストした。

既定は`sakura.OPTS`。`opt=()`で元のループ、各追加optを除けば比較経路を選べる。
音声送信ビュー全14種類の事前予約は`opt=sakura.STEADY_OPTS`で選ぶ。
事前予約はheap配置によってVMフレームの確保を遅くする場合があったため既定から外した。
既定は必要な長さを初回だけ保持する。`hudround`有効時は整数の帯域・サンプル数計算も使う。
最初の20秒に見えた小量のheap純増は、この有限の初期キャッシュ等を含む。

最後の統計なし20秒は1200更新、1199 COMMIT確認、**59.94 displayed/s**、全エラー0。
確認カウンタは既存の`wait_status(COMMIT_BUSY, 0)`が成功した後だけ増え、
追加の読出しはない。最後の未確認COMMITは数えない。

`proc`はCOMMIT同期フェーズ全体と統計用読出しを除く従来の定義。
同期フェーズにはSTATUSポーリングのCPU・IOコストも含み、純粋なidle時間だけではない。
統計の更新・heap標本読取りはさらに実際の表示間隔に影響する。
そのため統計付きcadenceと、追加読出しのない確認カウンタのthroughputを区別する。
また、初回と繰返しでheap配置が変わるため、最初の20秒と続く60秒を両方載せた。

## 総確保を数えて分かったVMの制約

v1.26の`py/objfun.c`では、`VM_MAX_STATE_ON_STACK`が4 byte×11 = 44 byte。
これを超えるPython関数のVM状態はheapに取り、復帰時に明示的に解放する。
`py/gc.c`は小さい空き穴から大きな連続領域を探すため、heap配置が呼出し時間に影響する。
この確保・解放は、GCを無効化して標本を取ったとしても純増には現れない。

GC allocatorの成功回数・block丸め後のbyte量・collection開始数を数える診断ファームを作った。
標本差分ではなく、ループの開始後から終了までを直接数える。

| 診断 | 統計なしの結果 | 総確保 | 実GC |
|---|---|---:|---:|
| 通常VM 44 B、short導入前 | 20秒・1130更新 | 36293回・3262448 B | 0 |
| 通常VM 44 B、直接メソッドでshort | 5秒・291更新 | 7751回・697520 B | 0 |
| VMのCスタック側上限256 B、直接メソッドでshort | 20秒・1200更新 | **0回・0 B** | **0** |

通常VMで残るのは、主にこのVM呼出しフレーム。後者の通常設定の測定では
約26.6回・2397 B/更新であり、heap純増0と混同できない。
例外・範囲外の大きなカウンタ・停止時の表示などは別で、garbage-freeなhot pathの対象外。

さらに`py/objboundmeth.c`は、5個以上の引数を取る束縛メソッドを変数に保持して呼ぶと
一時的な引数配列をheapに取る。初期のshort実装ではこれで32 B/回が残った。
通常の`link._fast(...)`というメソッド呼出しに直して除去した。
残っていた1回16 Bは`ipoll`の初回tupleで、入力を消費せず起動時に移した。

診断上限256 Bの最終トレース（`gross256-direct.txt`）は、統計あり／なし各20秒で
総確保0・GC 0、GC enabled=True。統計ありの通常p50/p95/p99/最大は
12.4/12.8/13.2/13.4 ms、HUD平均16.19・最大20.6 ms、cadence 1174/13、
**59.33 displayed/s**。統計なしは59.99 updates/s。

このしきい値変更は診断専用で製品には入れていない。RP2のCスタックは8 KBであり、
一般化には深い呼出し・thread経路のスタック余裕等を検証する必要がある。
`build_gc_counters.py`は元の3つのCファイルを必ず復元し、通常設定でも再ビルド済み。
実機もfw-ABCへ戻して最終計測した。診断UF2は`fw-gccount44.uf2`／`fw-gccount256.uf2`。

## 未達と次の対象

通常更新のp95は最終20秒13.4 ms、続く60秒13.6 msだが、最大は14 msを超える。
HUD最大34.9／30.2 msも16.67 msに未達。総確保ゼロは通常VM設定では未達で、
呼出しフレームを除くためにランタイム側の検討が必要と分かった。
固定のlive setでの明示的`gc.collect()`も約23.8〜23.9 msで、単発の停止予算は超える。
garbageを作らず回避することと、collector自体を16.67 ms以内にすることは別課題。

次は通常VMでのフレーム確保コストをどう扱うかと、音符開始・PCM statusポーリングが重なる
HUD更新のCPU／転送を詰めること。音の開始時刻・busy・エラーの契約を保つ必要がある。
720pは引き続き実機未計測。
