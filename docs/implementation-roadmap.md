# 開発ロードマップ

現行の機能・検証結果は[検証状況](validation-status.md)にまとめる。この文書は残る作業と拡張方針を扱う。

## 推奨する進め方（2026-10-24）

次の目標は、外部ホストから画像・sprite・音源を更新でき、起動・復帰・連続動作の証拠を添えて配布できる初版とする。描画機能を増やすより、実機接続、タイミングの安定化、ホストソフトの整備を優先する。

この計画はリポジトリ内の実装・検証記録に基づく提案であり、新しい実機試験の結果ではない。文書上の検証対象`bfd2178`と現在のチェックアウトの対応を最初に確認し、過去の合格を現在の成果物へ無条件に引き継がない。製品範囲のv0.1とレジスタABI 0.2は別に管理する。

### 段階と依存関係

工数は主担当1名の実作業日数の概算。機材調達・連続試験の待ち時間と、原因不明の不具合修正は含まない。M0完了後に再見積もりする。M2とM3は独立して進められ、W65C02S機材待ちの間もSPI側の作業を進める。

| 段階 | 優先度・目安 | 実装・改善する内容 | 完了条件・次への条件 |
|---|---|---|---|
| M0: 基準を固定 | 最優先・2〜3日 | 対象commit、ツール版、10構成、制約、既存試験を一覧化。回帰・P&Rを再実行し証拠manifestを作成 | 現行版の合否と未測定項目が区別され、同じ入力から再実行できる |
| M1: ABIとホスト基盤 | 高・4〜6日、M0後 | 機械可読レジスタ定義、SV/C/ca65定数生成、共通アクセス規約、CI再現性の改善 | ABI 0.2との全offset・bit・初期値一致、生成差分検査、既存回帰合格 |
| M2: SPI→QSPI実機 | 高・5〜8日、M1後 | MCU用ドライバ、診断プログラム、VRAM uploader。低速SPIから開始しQSPIへ進む | 両方式でID/ABI、VRAM照合、IRQ、sprite・音源更新、BUSY待ちと復帰を実機確認 |
| M3: HDMI・タイミング | 高・5〜10日、M0後に着手可 | critical path改善、OSER10 reset評価、複数sink試験、異常診断の整備 | 対象構成のSTA合格、例外の根拠と残余リスクを記録、規定の互換性試験合格 |
| M4: W65C02S接続 | 高・5〜8日、M1と外部回路準備後 | reset保持・decode/OEの回路確認、ca65/ld65サンプル、CPU固有のI/O規約検証 | 実CPUでM2相当の機能確認、起動前reset保持、バス波形とsetup/holdの実測合格 |
| M5: 初版候補を固定 | M2〜M4後・2〜4日 | サンプル、配線・書込み手順、既知制約、bitstreamと証拠一式を梱包 | 同一候補版で回帰・P&R・実機受入の証拠が揃い、クリーン環境から手順を再現できる |

M4を待つ間はSPI/QSPI向けの評価版を配布可能とするが、W65C02S検証済みの初版とは扱わない。機材不足・測定不能は未完了として残す。

### M0・M1: 変更を検証できる基盤

1. `tools/test-verilator.sh`、設計検査、依存hash検査、Gowinビルド・STAの結果を対象revisionへ紐付ける。`reports/<revision>/<tool-version>/<configuration>/`のmanifestにcommand、source/bitstream hash、CST/SDC、合否を記録する。大きな生成物はGit外の保存先と保持方針を決める。
2. CIのVerilatorを既存実績のある版を候補として固定し、版変更を独立した変更として検証する。現在のlog保存に、失敗時の画像・PCM・差分・必要時の波形を加える。タイムアウトと固定seedを設定し、意図的な失敗で診断資料が取得できることも確認する。
3. `spec/`に直接・EXT・音源レジスタのoffset、access種別、bit、reset値、副作用、対応ABIを定義する。SV/C/ca65定数と文書表を生成し、重複offset・予約bit・生成漏れをCIで拒否する。生成定義だけを正解とする試験に置き換えず、独立モデルと手書きの境界試験を残す。
4. SDKの古いABI 0.1表記と、ホスト仕様の「ABI 0.2で検討」という将来表記を整理する。機能追加の版番号は互換性評価後に決める。文書のPhase番号とこの計画のM番号は別物と明記する。

### M2・M4: 外部から使える最小SDK

最初の縦通しは「READY待ち→ID/ABI/CAPS→背景色→VRAM書込み/読戻し→sprite移動→6ch音源更新→IRQ応答」とする。デモ内sequencerではなく、公開インターフェースを通した成功を記録する。

- 共通層: timeout付き待機、FIFO空き確認、FILL/FENCE/COMMIT、VRAM読戻し、音源snapshot、wave bank交換。拒否時のaddressと副作用を考慮し、結果が不明な処理を無条件に再送しない。
- SPI/QSPI層: 配線表・ホストfirmware・ビルド手順を用意する。QSPIの方向切替、count付きread、BUSY、途中中断、reset復帰を確認する。SCKは低速から段階的に10MHzまで評価し、最大実測値と保証対象を区別する。
- W65C02S層: I/O baseとROM/RAM配置をboard別linker設定へ分離する。実回路の配置確定前に動作済みのバイナリを装わない。RMW禁止、indexed dummy read、IRQ中のindexed/address共有をAPI規約で扱う。
- ホスト側のasset変換: palette/tile/map/OAMとwaveデータの変換・サイズ検査・読戻し照合を用意する。既存デモ資産生成を再利用できるか評価し、画像編集GUIは初版の必須にしない。

測定には転送byte数、経過時間、BUSY待ち時間、FIFO拒否、adapter late、描画異常を含める。最大sprite負荷・全音源稼働中に転送し、帯域不足が通信・キュー・描画枠のどこにあるかを判断する。追加の高速転送機能はこの測定後に選ぶ。

### M3: 安定性と診断

- タイミング: 現行記録の720p最小setup slackは+0.029〜+0.095nsと小さい。まず同じEDA・構成でcritical pathを比較し、decode、fanout、配置、必要なpipelineを小さく変更する。数値だけを良くする例外追加は行わない。必須条件はsetup/hold WNS>=0、TNS=0、未制約同期パス0。改善目標の余裕値はM0の再測定後に決定し、変更前後を保存する。
- OSER10 reset: STA対象外のrecovery/removalについて解除シーケンス、clock/PLL lockとの関係を調べ、reset位相を変えた試験と実機反復を行う。例外が残る場合は根拠・評価範囲・未保証部分を明示する。起動成功だけで経路全体の保証としない。
- 互換性: [実機試験表](p1-07-hardware-test.md)の2機種以上×2ケーブル、起動20回、抜挿10回、各1時間を実施する。既存の固定テスト音版に加え、配布対象の480p/720p統合構成で動的更新時も確認し、構成別に記録する。
- TCL無信号: 同じ電源・ケーブル・入力条件で公式サンプルとKaguraを比較し、条件を1つずつ変える。原因未特定のまま対応済みとしない。一般の受入試験と原因調査を別に記録する。
- 診断: 現状のsticky flagで分かる「発生の有無」と回数を区別する。line underrun、audio under/overflow、PLL unlock、adapter lateの観測経路を一覧化し、必要なカウンタは診断構成から導入する。公開レジスタ追加時はABI/CAPSと資源・STAを再評価する。

### M5: 初版の受入ゲート

初版候補では仕様・RTL・制約・host firmware・サンプルを固定する。候補変更時には影響範囲の試験を再実行し、最終配布版との対応を確認する。

| ゲート | 必要な証拠 |
|---|---|
| 機能 | 既存の全画素・音声参照モデル・queue/IRQ/host回帰合格。未実施項目をpassに含めない |
| 資源・期限 | 対象構成がデバイスに収まり、renderer上限2633cyclesと構成別のguard/ホスト枠を維持 |
| STA・CDC | 対象構成ごとの結果、CDC/reset例外一覧、OSER10評価結果と残る制約 |
| 実機 | SPI/QSPI・W65C02S各接続の記録、電源投入・復帰、複数sink受入、通常負荷で異常なし |
| 配布 | source/bitstream hash、ツール版、配線、書込み・復旧手順、SDKサンプル、既知制約 |

実機音声のsample完全性やTMDS電気特性は専用計測なしに保証しない。未測定なら配布資料にも明記する。機能試験、互換性試験、規格適合の主張を混同しない。

## 初版の範囲と変更方針

背景1面、1024パターン、64登録sprite・16個/line、6ch音源、wave最大256sample/ch、CPU 3.375MHzを基準とする。描画は2633 system cycles/論理ラインの設計上限を維持する。デモ版はart ROMによりBSRAM 26/26を使用するため、追加機能は資源・配置の再評価を伴う。

仕様削減や変更は原因・実測・比較案・失う機能・回復条件を設計判断へ記録する。sprite数、pattern数、画面高などホストに見える変更はCAPS/EXT/ABIと文書を同時更新する。資源の削減案は[資源予算](resource-budget.md)を参照。

## 後続拡張

初版ゲート通過後は、次の順で小さな評価を行う。すべてを一度に実装する計画にはしない。

| 順序 | 候補 | 着手条件・評価結果 |
|---|---|---|
| 1 | サンプル・制作支援 | 外部ホスト版の小さなゲーム/HMIサンプル、font/tile/map変換を追加。初回導入の手順数と資産転送時間を測る |
| 2 | burst転送・block read・COPY | M2で帯域不足を再現できた場合。追加前後の実効転送量、キュー効率、描画期限、資源を比較 |
| 3 | SCK直接clock・8080バス | 現行方式では利用目的を満たせない場合。CDC・I/O制約・ピン・SDKの増分を含めて採否判断 |
| 4 | PSRAM・PCM・bitmap・raster拡張 | 必要帯域、メモリ構成、ABI、互換性を別設計として先に提示。Tang Nano 9K内の実現性を評価してから実装 |
| 候補 | SPI Flashアセットローダ | 下記。BSRAM不足でM3の配置改善が行き詰まった場合は、art ROM置換に限り前倒しを検討 |

### SPI Flashアセットローダ（候補）

基板上の外付けSPI Flashにfont・pattern・palette・waveを格納し、コマンドでVRAMへ転送する。フォント表示専用機能ではなく汎用の転送経路として設計する。

- 目的: ホストの起動時転送の削減、ホストなしの起動・診断画面、デモart ROMの置換によるBSRAM回復、1024 patternに収まらない日本語fontの必要文字だけの読込み。
- 方式: 描画中にFlashを直接読まない。Flashからpattern/palette/wave RAMへのコピーに限り、FILLと同様にVRAMの空き枠だけで進めてコマンド順を守る。1bpp格納から前景・背景index指定で4bppへ展開する形式を評価する。
- ABI: コピーコマンド、CAPS bit、進捗・エラー状態を別仕様で定義し、互換性評価後に版番号を決める。
- 着手前の確認: Flash（P25Q32想定）のFPGA接続pinを回路図で確認しpin一覧へ追加する。外部Flashへの書込み・照合手順を確立する（内蔵Flashの`Verify Failed at 0`と同様の未解決表示を照合成功と扱わない）。
- 評価: 転送速度（単線SPI 27MHzで約3MB/s、pattern全体32KBで約10msの見込み）、LUT/FF増分、BSRAM削減量、STA、描画期限への影響を実測する。

HMIは利用例として候補に置く段階とし、タッチ入力やウィジェット描画のFPGA実装は前提にしない。具体的な用途が決まった時点で、ホストソフトで実現する部分とVDPに必要な拡張を分ける。

## 直近の着手順

1. M0の対象revision・構成・ツール・機材一覧と基準結果を揃える。
2. CI版固定・失敗時artifact保存を1つの変更として実装する。
3. レジスタ定義と生成器を導入し、既存ABIとの一致を確認する。
4. SPIの最小診断firmwareとVRAM uploaderを用意し、入手可能なMCUで縦通しする。
5. 同時期に720pのcritical pathとOSER10 resetを評価し、CPU回路と追加sinkの準備を進める。

各変更には目的、完了条件、必要な試験、対象構成、証拠の保存先を添える。機能追加と大きな構造変更は分離し、失敗原因を比較できる単位で進める。

PSRAM、PCM、COPY、DMA、bitmap、raster更新は初版の必須範囲外。別仕様・ABIで管理する。SPI/QSPIのSCK直接clock化、burst VRAM転送、8080型パラレルバスは[ホスト仕様](host-interface.md)に候補を記載する。まず現行の実機接続・互換性・タイミングを確認してから評価する。

CPUのROM/RAM配置はホスト依存としてlinker設定へ分離する。C++ harnessやCPUエミュレータを使う命令副作用の試験は未実装で、現在のSystemVerilog bus modelによる検証と区別する。
